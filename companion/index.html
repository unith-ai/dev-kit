Chapter 4 20 min · the core

        
Plugin mode — bring your own LLM

        
Your server becomes the brain. UNITH sends you every user message; whatever you return is what the digital human speaks. Your LLM, your SLM, your rules, your RAG — full control.

        

          
terminal · your backend, in this order

          
# 1. the demo backend server (zero dependencies — its only job is to SHOW
#    what arrives and how you answer):
npm start

# 2. expose it — ngrok prints a public https URL:
ngrok http 3000

# 3. copy that URL into the panel → Tunnel URL. The head must be created
#    ALREADY POINTING at it (next step).

        

        
Order matters: the plugin head stores the endpoint URL at creation — get the tunnel up and the URL into .env / the panel before creating it. (If the tunnel URL changes later, update the head's pluginOperationalModeConfig with PUT /head/update.)

        
ngrok gotcha: the terminal panel truncates the Forwarding line at the window edge — easy to copy a broken URL (missing .app). Copy it from ngrok's web interface at 127.0.0.1:4040 instead, and sanity-check with curl TUNNEL_URL/health before creating the head.

Own the replies. Everything the head says is decided in server.js → handlePlugin() — two decision points:

        

          
server.js · where to edit

          
// 1. TRIGGERS — keywords fire actions AND custom replies:
if (/\b(price|pricing|cost)\b/i.test(userText)) {
  fireTrigger('pricing_intent', userText);   // → CRM, Slack alert, ticket…
  return reply('Great question. Our team tailors pricing to each use case…', started, asTraces);
}

// 2. THE DEFAULT ANSWER — this line IS the brain. Swap it for your model:
// const answer = await yourLLM(userText);   ← OpenAI, your own SLM, RAG…
const answer = `You said: "${userText}". …`;

        

        

          Live-edit exercise: make it use the session metadata
          
Replace the const answer line with this, restart (Ctrl+C → npm start), and talk again — the head will tell you what device you are on:

          

            
server.js · paste over the answer line

            
const device = meta?.request_metadata?.essential?.device_info?.device_type ?? 'device';
const answer = `I can see you are talking to me from a ${device}. Everything I know about you came through YOUR server.`;

          

          
Every turn, the console shows the full round trip: the incoming payload, 💬 reply → "…", and the handler latency.

        


        
Finale: plug in a real local SLM. The demo server ships ready to use a small language model running on your own machine (Qwen3.5-4B, open weights, via an OpenAI-compatible local server) — no cloud, no API key, the brain runs on your hardware:

        

          
terminal · start the local model, then flip the switch

          
# 1. serve the model locally (first run downloads ~2.3 GB):
uvx --from 'mlx-lm>=0.30' --python 3.12 mlx_lm.server \
  --model mlx-community/Qwen3.5-4B-MLX-4bit --port 1234 \
  --chat-template-args '{"enable_thinking": false}'

# 2. in .env:  LOCAL_LLM=on   → restart the server (Ctrl+C, npm start)

        

        
Talk to the head again: now every reply is generated by the local model, and the console prints its cost honestly — 🧠 local LLM answered in ~2700 ms — running on THIS machine.

        
The latency trade-off: a 4B model on a laptop adds ~2–3 s per turn; the same model on a proper GPU (or a fast provider like Groq) adds a fraction of that. That trade-off — model size × hardware × latency — is now YOUR dial to turn. Note the triggers still fire before the LLM: rules where you need certainty, model where you need conversation.

Raw response

        

        
⚠️ Tool parameters format: parameters is a list of { "name": "…", "description": "…" } objects — not a JSON schema, not a plain map, and no field left unfilled. A malformed tool doesn't just fail the call: the head won't load at all (the NLP session throws on init).

        
A tool is only half the feature — the prompt is the other half. The settings declare what the tool is; the system prompt tells the head when to call it:

        

          
the prompt block that activates the tools

          
LEAD CAPTURE: your first goal is to learn the visitor's name, and after that
their email address. Ask naturally, one thing at a time. The moment the user
provides their email address, call the capture_lead tool with the parameters
name and email.
POLICY QUESTIONS: if the user asks about their policy or its status, call the
check_policy_status tool and answer with what it returns.
TOOL RESULTS: after any tool responds, follow the instructions contained in the
tool result faithfully.

          The same calls from the terminal
          

            
terminal · register / list / delete

            
# register — set true only for the events you want; the response returns
# the sharedKey for HMAC verification.
# NOTE: posting again ADDS another registration (it does not update):
curl -X POST 'https://platform-api.unith.ai/head-events' \
  -H 'authorization: Bearer YOUR_BEARER_TOKEN' \
  -H 'content-type: application/json' \
  -d '{
    "headId": "HEAD_ID",

    "startConversation": false,
    "endConversation": true,
    "timeoutConversation": false,
    "inactivityWarning": false
  }'

# list the registrations of a head (includes each sharedKey):
curl 'https://platform-api.unith.ai/head-events?headId=HEAD_ID' \
  -H 'authorization: Bearer YOUR_BEARER_TOKEN'

# remove one by its id (from the list above):
curl -X DELETE 'https://platform-api.unith.ai/head-events/REGISTRATION_ID' \
  -H 'authorization: Bearer YOUR_BEARER_TOKEN'

Part 2 — the SDK: full frontend control

        
With the SDK (@unith-ai/core-client, v3) you sit between the user and the head — a turn-based session whose whole state is exposed as observables, rendered into any element you own. This is the core of it:

        

          
typescript · @unith-ai/core-client v3

          
import { Session } from '@unith-ai/core-client';

// 1. Connect and render the idle avatar (the element needs width + height):
const session = await Session.startDigitalHuman(
  document.getElementById('avatar'),
  { orgId: 'YOUR_ORG', headId: 'YOUR_HEAD', apiKey: 'YOUR_KEY' },
);

// 2. Everything is an observable — subscribe to what you care about:
session.turn.subscribe((t) => console.log(t.state));  // idle | thinking | ai-speaking | interrupting
session.messages.subscribe(renderTranscript);          // the full transcript, on every change
session.caption.subscribe(showCaption);                // text as the avatar speaks

// 3. Playback MUST start from a user gesture (browsers block auto-audio):
startButton.onclick = () => session.startSession();

// 4. Drive it: send messages (only while turn is idle), interrupt, control:
session.sendMessage('The user just opened the pricing page.');
session.stopResponse();      // barge-in interrupt
session.toggleMute();  session.toggleCaptions();  session.toggleMicrophone();
await session.endSession();  // clean teardown

        

        
The gesture rule: startDigitalHuman() connects and shows the idle avatar; startSession() begins audio/video and must run inside a click — otherwise the head loads but never speaks. Every demo below has a ▶ Start button for exactly this reason.

        
See the SDK in action — first the playground, then three layouts that prove the frontend is entirely yours:

        

          
          
The full API surface, live: state chips (connection · turn · mic · muted · captions), transcript, event log of every observable, interrupt, mute, captions, microphone, timeout rescue, teardown. Hover any control — every button explains itself.

          
          
The head as a circle you can drag anywhere on the screen. Collapsed it shows the idle preview without opening a connection; click it and it expands, connects and talks.

          
          
The head as the page: fullscreen video with the UI overlaid on top — brand, live turn indicator, cinematic captions and a floating input.

          
          
The page drives the conversation: as you scroll, each section sends context and the head narrates what you are looking at. Any UI event — scroll, click, form — can talk to the head.

        

        
⚠️ Careful with the concurrency limit: every open conversation holds a slot, and a developer account has 3 concurrent slots — three users talking at once, and every open tab counts. Over the limit, sessions are refused or dropped (the SDK reports it as a disconnect with reason concurrency_limit_reached, and these demos show a warning) — so if a head goes quiet while you test in several tabs, close one. Concurrency is a main driver of pricing, and the right size depends on your use case. To size yours: sales@unith.ai.

Custom avatars — your own head visuals

        
The face is an asset you can create: a short video becomes a head visual, and any head can wear it.

        
Guidelines: MP4, 1280×720 @ 25 fps, short (≈10 s) and light (a few MB), first and last frames matching (it loops). Two modes: a single idle loop, or an expressive state (idle + expressive movement, split at cut_timestamp).

        
Step 1 — upload the video. Pick the MP4, check it in the preview, and upload. No suitable footage? The kit includes two proven samples: sample-avatar.mp4 (a calm idle loop) and sample-avatar-expressive.mp4 (3 s of calm idle, then expressive movement — made for the expressive state below). The platform returns a temporary token that identifies the uploaded file for the next step:

Step 2 — create the visual. This starts the processing job (face detection, loop preparation). The upload token travels in a header, and there are two flavours: a single idle loop (the default), or an expressive state — the visual has a calm idle AND a livelier state the head switches to while speaking. Every body field is optional; these are the defaults for the single loop:

        

          

            
ParameterValueWhat it does

            
              
x-head-video-token-idheaderThe token from step 1 — which uploaded file to process

              
updatefalsefalse = new visual; true = reprocess an existing one

              
detector_versionv2Face-detector generation — v2 is the recommended one

              
detector_threshold0.2Face-detection confidence: lower accepts harder shots, higher is stricter

              
modedefaultdefault = one idle loop; two_loops = idle + active states

              
cut_timestamp0.1Two-loops only: the second (in the video) where idle switches to active

            
          

        

        

          The expressive-state preset (what changes and why)
          

            
body · idle + expressive state

            
{
  "update": false,
  "detector_version": "v2",
  "detector_threshold": -0.2,        ← more permissive: expressive footage moves more
  "mode": "two_loops_streaming",     ← the expressive-state mode
  "cut_timestamp": 3.0,              ← the second where calm idle ends and expression begins
  "template_zoom_factor": 1.05,      ← slight zoom for framing consistency between states
  "mask_diameter_scale": 1.05,       ← blending mask tuning (size, position, softness)
  "mask_offset_factor": 0.02,
  "mask_sigma": 0.8,
  "debug": false
}

          

          
Your footage must match cut_timestamp: calm, loopable idle up to that second, expressive movement after it. The included sample-avatar-expressive.mp4 is cut at exactly 3.0 s.
